# Правила работы с Atlas

## Границы проекта

- Сохраняй разделение на изолированные плагины в `pkg`: доменная логика — в
  `service.go`, доступ к БД — в `repository.go`, модели — в `entity.go`.
- Регистрируй новые плагины и их конфигурацию через `pkg/plugins.go`; не добавляй
  доменную логику в `cmd/atlas/main.go`.
- Размещай transport-слой и внешние API в `app`. `app.API` — единственный адаптер
  JSON-RPC; регистрируй transport через него, а не через доменные сервисы.
- Для JSON-RPC используй генератор Goppy: контракт размещай в `app/types`,
  директивы — в `app/types/tb.go`, а сгенерированный код — в `app/transport`.
  Не редактируй `app/transport/jsonrpc_server_*.go` вручную; после изменения
  контракта запускай `go generate ./...`.
- Считай `atlas-runner` независимым будущим сервисом. Не добавляй в него логику
  `atlas` без явного требования.
- Не создавай и не упоминай UI в `web`: такого каталога в проекте сейчас нет.

## DHCP

- Поддерживай разделение DHCP-кода: JSON-RPC-контракт и внешние DTO — в
  `app/types/dhcp.go`, реализация transport-контракта — в
  `app/api_dhcp_service.go`, сгенерированные handlers и модели — в
  `app/transport`, валидация и lifecycle — в `pkg/dhcp/service.go`,
  конфигурация — в `config.go`, SQL — в `repository.go`.
- Не импортируй Web или JSON-RPC в `pkg/dhcp`. Предоставляй нужные API методы
  публичными context-aware методами `dhcp.Service`; реализация контракта в `app`
  вызывает только их.
- Храни модели БД и домена в `pkg/dhcp/entity.go` без JSON-тегов. Не передавай их
  напрямую через транспорт: преобразуй в DTO и обратно внутри `app`.
- Изменяй конфигурацию DHCP только в draft. Активной она становится исключительно
  после успешного `dhcp.apply`.
- Не заявляй, что DHCPv4 выдаёт адреса, пока не реализованы UDP/67, packet loop,
  allocation и тесты протокола.

## Миграции

- Добавляй изменения схемы только новым файлом в `pkg/database/migrations` со
  следующим порядковым номером. Никогда не изменяй уже созданную миграцию.
- Учитывай, что `orm.WithMigration(database.Migrations())` использует embedded FS,
  применяет миграции только к SQLite-тегу `master`, сортирует их по имени и хранит
  только basename без checksum.
- Пиши миграции небольшими и, где возможно, идемпотентными: SQL одного файла не
  выполняется общей транзакцией. При ошибке часть запросов может примениться, но
  имя миграции не будет сохранено, и файл повторится на следующем запуске.

## Качество кода

- После любых изменений Go-кода обязательно запускай `gofmt` для всех Go-файлов
  проекта, а не только для затронутых файлов.
- После изменений Go-кода обязательно запускай `make lint`: он применяет
  `goimports` и `gofmt`, а затем проверяет качество кода через `golangci-lint`.
- Используй `go-mcp` для диагностики Go workspace и навигации по символам; перед
  завершением Go-изменений запускай `go_diagnostics` для затронутых файлов.
- Перед рефакторингом находи все вызовы через `go_symbol_references`; для поиска
  символов используй `go_search`, а для проверки публичной границы пакета —
  `go_package_api`. Переименование символов выполняй через `go_rename_symbol`.
- Перед изменением незнакомого или связанного с несколькими пакетами Go-файла
  используй `go_file_context`, чтобы проверить его зависимости и влияние.
- При проверке зависимостей используй `go_vulncheck`; если сетевой доступ к базе
  уязвимостей заблокирован, укажи это в результате проверки.
- Никогда не объявляй структуру внутри функции, включая `var x struct { ... }`.
  Выноси доменные и БД-модели в `entity.go` соответствующего плагина, а внешние
  API-модели — в `app/types/<domain>.go`.
- Не игнорируй ошибки через `_ =`: возвращай их вызывающему коду либо логируй через
  `go.osspkg.com/logx`, если безопасно продолжить работу.
- Перед завершением изменений запускай `make lint`, `go test ./...` и
  `git diff --check`. Отдельно сообщай о проверках, заблокированных sandbox или
  сетью.
- При проблемах с правами на Go cache используй отдельный writable `GOCACHE` в
  `/tmp`.
